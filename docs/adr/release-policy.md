# 发版策略：内部改进不单独触发发布

状态：已采纳

## 背景
Ember2 使用 Tauri updater 基于版本号触发更新。若每次内部结构改进都切版本，会给用户制造无意义的下载和重启，也让版本历史被技术细节稀释。

## 决策
无用户可感知变化的内部改进只合入 `main`，不修改版本号、不打 tag、不触发 Release/updater。发布由有用户价值的功能或修复驱动，内部改进随下一个发布版本自然带上。

"用户可感知变化"指：新增功能、用户可见的缺陷修复、界面/交互变化、可感知的性能提升。纯重构、类型铺垫、门禁加固、测试补充不属于此列。

## 例外
若某内部改进修复的问题已被用户实际报告（即使表现为边缘输入），应单独走 patch 发布，不等待下一个功能版本。

## 后果
- 版本号只反映用户价值，不反映内部工作量。
- 内部改进的验证依赖 CI 和主干测试，而非发布流程。
- 协作者需在 CHANGELOG 的 `[Unreleased]` 下持续记录，发版时按需筛选用户可见条目。
